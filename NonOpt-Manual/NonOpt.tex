\section{Introduction}

NonOpt (Nonconvex, Nonsmooth Optimizer) is an open-source C++ software package for solving unconstrained minimization problems.  It is designed to locate a minimizer, or at least a (nearly) stationary point, of an objective function $f : \mathbb{R}^n \to \mathbb{R}{}$, which is assumed to be locally Lipschitz.  That is, given such an objective function $f$, the software contains algorithms that are designed to solve problems of the form
\begin{equation*}
  \min_{x \in \mathbb{R}^n}\ f(x).
\end{equation*}
The objective function $f$ can be nonlinear, nonconvex, and/or nonsmooth.  For further information, see \cite{CurtZebi2025}.

This manual documents NonOpt version \nonoptversion.

%************
% Subsection
%************
\subsection{Algorithm Overview}

NonOpt contains implementations of a collection of algorithms, including gradient-sampling and proximal-bundle methods, each equipped with quasi-Newton techniques for improving practical performance.  You can choose between different strategies for the search direction computation, approximate Hessian approximation update, line search, point-set update, symmetric matrix storage, and termination.  For more information on the implemented algorithms, see \cite{CurtZebi2025}, which in turn references the algorithms developed in \cite{CurtLi22,CurtQue13,CurtQue15,CurtRobiZhou20}.

% Subsection

\subsection{Availability}

This puts very few restrictions on the use and reuse of the software. This license has been selected since the goal of open-source software is continuous development and improvement. \subsection{Compiling NonOpt}\label{sec.compiling}

A C++ compiler is required to compile the NonOpt library. Building NonOpt also requires:

\begin{itemize}
  \item BLAS (Basic Linear Algebra Subroutines). Many operating systems provide precompiled and optimized
libraries for these subroutines.  One could also obtain the source code from \href{www.netlib.org}{www.netlib.org}.  However, it is recommended to use an optimized BLAS implementation.
  \item LAPACK (Linear Algebra PACKage).  As with BLAS, many operating systems provide precompiled and optimized libraries, but the source code can also be obtained from \href{www.netlib.org}{www.netlib.org}.
\end{itemize}

After obtaining NonOpt, an environment variable needs to be set:
\begin{itemize}
  \item \texttt{\$NONOPTDIR} should point to the NonOpt root directory of the distribution that you obtained. This root directory is the one containing the \texttt{README.md} file for the distribution.
\end{itemize}

After this environment variable has been set, the NonOpt library can be built by issuing the commands below.  Here, and throughout this document, ``\texttt{>}'' indicates your terminal prompt.

\begin{verbatim}
> cd $NONOPTDIR/NonOpt
> make
\end{verbatim}

This should make the libraries in each of the \texttt{src}, \texttt{problems}, and \texttt{tests} subdirectories.  It should also
make two executables, \texttt{runExperiment} and \texttt{solveProblem}, in the \texttt{exes} subdirectory, as well as a few executables in the \texttt{mpc} subdirectory, which are provided to reproduce the numerical results for the experiments in \cite{CurtZebi2025}.

The Makefiles build with optimizations enabled (\texttt{-O3 -DNDEBUG}) by default.  An unoptimized build with debugging symbols can be obtained in any of these directories by issuing \texttt{make debug} instead of \texttt{make}.

The Python and AMPL interfaces are built separately; see \S\ref{sec.python} and \S\ref{sec.ampl}, respectively.

\subsection{Compiling NonOpt with CMake}\label{sec.cmake}

As an alternative to the Makefiles described in \S\ref{sec.compiling}, NonOpt can be built with CMake (version 3.15 or later).  The two build systems coexist; neither interferes with the other.  From the NonOpt root directory, issue:

\begin{verbatim}
> cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
> cmake --build build -j
\end{verbatim}

CMake locates BLAS and LAPACK automatically.  To request a specific implementation, configure with, e.g., \texttt{-DBLA\_VENDOR=OpenBLAS}.  Libraries are placed in \texttt{build/lib} and executables in \texttt{build/bin}.  The build defaults to \texttt{Release} if no build type is specified.  NonOpt can also be installed, and then located by other CMake projects via \texttt{find\_package(NonOpt)}, by issuing:

\begin{verbatim}
> cmake --install build --prefix /your/install/prefix
\end{verbatim}

\subsection{Testing the Installation}

If the compilation has been successful, then a few unit tests and a minimization test can be run by issuing:

\begin{verbatim}
> cd $NONOPTDIR/NonOpt/tests
> ./testAll
\end{verbatim}

Standard output will reveal the results of the unit tests. If all unit tests are successful, then the script will continue to run a minimization test for a test problem that is implemented in \texttt{\$NONOPTDIR/NonOpt/problems}.  If a unit test fails, then the minimization test is not run.  In this case, it is possible (although not necessarily the case) that NonOpt will not run properly, or at least the performance that you will obtain by using NonOpt will not be as good as expected.  More detailed output from each unit test can be obtained by running each unit test separately. For example, the symmetric matrix class can be tested by issuing:

\begin{verbatim}
> cd $NONOPTDIR/NonOpt/tests
> ./testSymmetricMatrix
\end{verbatim}

The last line of the detailed output indicates whether or not the test was successful.  Each test executable, including \texttt{testAll}, also returns a process exit code of zero on success and nonzero on failure, so the tests can be run from a script.

If NonOpt was built with CMake as in \S\ref{sec.cmake}, then the same tests are registered with CTest and can all be run by issuing:

\begin{verbatim}
> ctest --test-dir build --output-on-failure
\end{verbatim}

\subsection{C++ Interface}\label{sec.cpp}

NonOpt comes with a set of test problems in the \texttt{\$NONOPTDIR/NonOpt/problems} directory.  The easiest way to interface your problem to NonOpt is to follow one of these as an example.

%***************
% Subsubsection
%***************
\subsubsection{Implementing a Problem}

For example, consider \texttt{MaxQ} implemented in \texttt{MaxQ.hpp} and \texttt{MaxQ.cpp} in \texttt{\$NONOPTDIR/NonOpt/problems}.  This problem is scalable, with the input \texttt{n} to the constructor dictating the dimension of the problem to be solved.  If your problem is not scalable, then the value of \texttt{number\_of\_variables} can be hard-coded. The remainder of an implementation of a problem can be understood in this example.  Overall, the functions that need to be implemented are those dictated in the header file \texttt{\$NONOPTDIR/NonOpt/src/NonOptProblem.hpp}.

\texttt{Note:} It is extremely easy to set up NonOpt for failure if you have bugs in your objective and/or
derivative implementations.  NonOpt comes equipped with a derivative checker that you can use to test your
implementation of your \texttt{evaluateGradient} function with respect to your \texttt{evaluateObjective} function.  See~\S\ref{sec.options} for instructions on turning on the derivative checker when your problem is being solved.

%***************
% Subsubsection
%***************
\subsubsection{Solving a Problem}

Suppose your problem is implemented in \texttt{YourProblem.hpp} and \texttt{YourProblem.cpp}.  If these files are located in \texttt{\$NONOPTDIR/NonOpt/problems}, then running \texttt{make} in this directory will add \texttt{YourProblem} to the \texttt{libNonOptProblems.a} library that is built in this directory.  Your problem can then be solved by adding it to the list of problems in \texttt{solveProblem.cpp} in \texttt{\$NONOPTDIR/NonOpt/exes}, then issuing:

\begin{verbatim}
> cd $NONOPTDIR/NonOpt/exes
> ./solveProblem YourProblem
\end{verbatim}

You might also implement your own executable to set up and solve your problem.

\subsection{Python Interface}\label{sec.python}

NonOpt provides a Python interface, built with \href{https://github.com/pybind/pybind11}{pybind11}, that exposes the solver as a module named \texttt{nonoptpy}.  A problem is defined in Python by subclassing \texttt{nonoptpy.Problem}, so no C++ needs to be written.  Objective and gradient values are exchanged as NumPy arrays.

%***************
% Subsubsection
%***************
\subsubsection{Building the Python Module}

In addition to \texttt{\$NONOPTDIR}, building the Python module requires that pybind11 and NumPy be installed, and that an environment variable point to the pybind11 headers:

\begin{itemize}
  \item \texttt{\$PYBINDDIR} should point to the pybind11 include directory, as reported by
        \texttt{python3 -m pybind11 --includes}.
\end{itemize}

The module can then be built by issuing:

\begin{verbatim}
> pip install pybind11 numpy
> cd $NONOPTDIR/NonOpt/python
> make
\end{verbatim}

This produces a shared object named \texttt{nonoptpy} followed by the extension suffix for your Python installation, e.g., \texttt{nonoptpy.cpython-311-darwin.so}.  The module is importable from any directory on your Python path; the simplest approach is to run your scripts from \texttt{\$NONOPTDIR/NonOpt/python}.

%***************
% Subsubsection
%***************
\subsubsection{Implementing a Problem in Python}

A problem is implemented by subclassing \texttt{nonoptpy.Problem} and defining the methods in Table~\ref{tab.python}.  Note that the Python signatures are not identical to their C++ counterparts: values that are returned through output arguments in C++ are, in several cases, returned directly in Python or written in place into a NumPy array.

\begin{table}[ht]
\centering
\begin{tabular}{|l|p{8.2cm}|}
\hline
\textbf{Method} & \textbf{Description} \\
\hline
\texttt{numberOfVariables(self)} & Returns the number of variables $n$ directly, as an integer. \\
\hline
\texttt{initialPoint(self, n, x)} & Writes the initial point in place into the NumPy array \texttt{x}.  Returns \texttt{True} on success. \\
\hline
\texttt{evaluateObjective(self, x)} & Returns $f(x)$ directly, as a float.  Note that this method takes only \texttt{x}; it does \emph{not} take \texttt{n}. \\
\hline
\texttt{evaluateGradient(self, n, x, g)} & Writes the gradient in place into the NumPy array \texttt{g}.  Returns \texttt{True} on success. \\
\hline
\texttt{evaluateObjectiveAndGradient(self, n, x, f, g)} & Writes the objective value into \texttt{f[0]}, where \texttt{f} is a \emph{list}, and the gradient in place into \texttt{g}.  Returns \texttt{True} on success.  Used only when the option \texttt{evaluate\_function\_with\_gradient} is \texttt{true}. \\
\hline
\texttt{finalizeSolution(self, n, x, f, g)} & Called once with the final point, objective value, and gradient.  Returns \texttt{True} on success.  This method is required: it must be defined even if it does nothing but \texttt{return True}. \\
\hline
\end{tabular}
\caption{Methods of a \texttt{nonoptpy.Problem} subclass.}\label{tab.python}
\end{table}

Arrays that are written in place (\texttt{x} in \texttt{initialPoint}, \texttt{g} in the gradient methods) are views onto NonOpt's own memory.  They should be filled element-wise or with in-place NumPy operations such as \texttt{g.fill(0)}; rebinding the name, as in \texttt{g = np.zeros(n)}, will \emph{not} communicate any values back to the solver.

%***************
% Subsubsection
%***************
\subsubsection{Solving a Problem in Python}

The following complete example implements and solves the \texttt{MaxQ} problem.  It is available, along with a Rosenbrock example, in \texttt{\$NONOPTDIR/NonOpt/python}.

\begin{verbatim}
import nonoptpy as nonopt
import numpy as np

class MaxQ(nonopt.Problem):

  def numberOfVariables(self):
    return 1000

  def initialPoint(self, n, x):
    for i in range(n//2):
      x[i] = i + 1
    for i in range(n//2,n):
      x[i] = -i - 1
    return True

  def evaluateObjective(self, x):
    return np.max(np.abs(x))**2

  def evaluateGradient(self, n, x, g):
    index = np.argmax(np.abs(x))
    g.fill(0)
    g[index] = 2 * x[index]
    return True

  def evaluateObjectiveAndGradient(self, n, x, f, g):
    f[0] = np.max(np.abs(x))**2
    index = np.argmax(np.abs(x))
    g.fill(0)
    g[index] = 2 * x[index]
    return True

  def finalizeSolution(self, n, x, f, g):
    return True

# Declare solver
solver = nonopt.Solver()

# Modify options from file
solver.options().modifyOptionsFromFile("nonoptpy.opt")

# Add file report
solver.reporter().addFileReport("report", "nonoptpy.out",
                                nonopt.ReportType.R_NL,
                                nonopt.ReportLevel.R_PER_ITERATION)

# Optimize
solver.optimize(MaxQ())

# Print a few statistics
print(f"Final objective ..... : {solver.objective()}")
print(f"Iterations .......... : {solver.iterations()}")
print(f"CPU seconds ......... : {solver.time()}")
print(f"Solver status ....... : {solver.status()}")

# Retrieve the solution
x = np.zeros(solver.numberOfVariables())
solver.solution(x)
\end{verbatim}

The \texttt{nonoptpy.Solver} object exposes the following methods.  The statistics correspond to the quantities reported at the end of a run; see \S\ref{sec.output}.

\begin{itemize}
  \item \texttt{optimize(problem)}: solves the given \texttt{Problem} instance.
  \item \texttt{solution(x)}: writes the final iterate into the preallocated NumPy array \texttt{x}, which must have length \texttt{numberOfVariables()}.
  \item \texttt{options()}: returns the \texttt{Options} object; see \S\ref{sec.options}.
  \item \texttt{reporter()}: returns the \texttt{Reporter} object, whose \texttt{addFileReport(name, file, type, level)} method directs output to a file.  The arguments \texttt{type} and \texttt{level} are values of the enumerations \texttt{nonoptpy.ReportType} (\texttt{R\_NL} or \texttt{R\_QP}) and \texttt{nonoptpy.ReportLevel} (\texttt{R\_NONE}, \texttt{R\_BASIC}, \texttt{R\_PER\_ITERATION}, or \texttt{R\_PER\_INNER\_ITERATION}).
  \item \texttt{objective()}, \texttt{stationarityRadius()}, \texttt{numberOfVariables()}: solution quantities.
  \item \texttt{iterations()}, \texttt{totalInnerIterations()}, \texttt{totalQPIterations()}, \texttt{functionEvaluations()}, \texttt{gradientEvaluations()}: iteration and evaluation counts.
  \item \texttt{time()}, \texttt{timeEvaluations()}, \texttt{timeNonOpt()}: CPU seconds in total, in function and gradient evaluations, and in NonOpt itself.
  \item \texttt{status()}: a value of the enumeration \texttt{nonoptpy.NonOpt\_Status}, e.g., \texttt{NONOPT\_SUCCESS}.  These correspond to the EXIT messages listed in \S\ref{sec.output}.
\end{itemize}

\subsection{AMPL Interface}\label{sec.ampl}

NonOpt can be used as a solver for problems modeled in \href{https://ampl.com}{AMPL} through the AMPL Solver Library (ASL).  In addition to \texttt{\$NONOPTDIR}, two further environment variables are required:

\begin{itemize}
  \item \texttt{\$AMPLDIR} should point to the directory containing the compiled ASL, i.e., the directory containing \texttt{amplsolver.a} and the ASL headers.
  \item \texttt{\$LAPACKDIR} should point to the directory containing your BLAS and LAPACK libraries.
\end{itemize}

The interface is then built by issuing:

\begin{verbatim}
> cd $NONOPTDIR/NonOpt/ampl
> make
\end{verbatim}

This produces the library \texttt{libAMPLProblem.a} and the executable \texttt{solveAMPLProblem}.  Given a problem written in AMPL and exported to a \texttt{.nl} file, say \texttt{YourProblem.nl}, the problem is solved by issuing:

\begin{verbatim}
> cd $NONOPTDIR/NonOpt/ampl
> ./solveAMPLProblem YourProblem
\end{verbatim}

Note that the \texttt{.nl} suffix is appended automatically and should be omitted from the argument.

\subsection{Changing Options}\label{sec.options}

NonOpt is designed to be flexible, offering various options, each of which can be changed from its default value, if desired.  For a complete list of options, along with their types, bounds, and default values, please see the \texttt{\$NONOPTDIR/NonOpt-Manual/options.txt} file.  A selection of the most commonly used options is given in Table~\ref{tab.options}.  Some safeguards have been added so that you cannot set an option to an illegal value, although it is possible that you could set an option to a value that will cause the optimizer to behave in strange ways.  If you provide a legal value (and the \texttt{Reporter} is issuing output to a report at a sufficient level), then a note will be printed (to a report) that the value for an option has been changed.  If you attempt to set an option to an illegal value, then similarly a note will be printed saying that a change was attempted, but the attempt was not successful (due to the provided value being illegal).  Options should be set with caution, or at least with sufficient knowledge of the underlying algorithms.

\begin{table}[ht]
\centering
\begin{tabular}{|l|l|l|}
\hline
\textbf{Option} & \textbf{Type} & \textbf{Default} \\
\hline
\texttt{print\_level}                & integer & \texttt{1} \\
\texttt{print\_level\_file}          & integer & \texttt{0} \\
\texttt{print\_file\_name}           & string  & \texttt{nonopt.out} \\
\hline
\texttt{cpu\_time\_limit}            & double  & \texttt{1e+04} \\
\texttt{iteration\_limit}            & integer & \texttt{1e+06} \\
\texttt{function\_evaluation\_limit} & integer & Infinity \\
\texttt{gradient\_evaluation\_limit} & integer & Infinity \\
\texttt{stationarity\_tolerance}     & double  & \texttt{1e-04} \\
\hline
\texttt{direction\_computation}      & string  & \texttt{CuttingPlane} \\
\texttt{approximate\_hessian\_update}& string  & \texttt{BFGS} \\
\texttt{line\_search}                & string  & \texttt{WeakWolfe} \\
\texttt{point\_set\_update}          & string  & \texttt{Proximity} \\
\texttt{qp\_solver\_small\_scale}    & string  & \texttt{DualActiveSet} \\
\texttt{qp\_solver\_large\_scale}    & string  & \texttt{InteriorPoint} \\
\texttt{symmetric\_matrix}           & string  & \texttt{Dense} \\
\texttt{termination}                 & string  & \texttt{Basic} \\
\hline
\texttt{derivative\_checker}         & string  & \texttt{FiniteDifference} \\
\texttt{DEFD\_check\_derivatives}    & bool    & \texttt{false} \\
\hline
\end{tabular}
\caption{Commonly used options.  See \texttt{options.txt} for the complete list.}\label{tab.options}
\end{table}

The value for an option can be changed in one of two ways:

\begin{itemize}
  \item In an executable.  After a \texttt{NonOptSolver} object has been declared (via \texttt{NonOptSolver nonopt;}), one can modify the value of an option via a statement such as:
  \begin{verbatim}
  nonopt.options()->modifyDoubleValue("cpu_time_limit", 600.0);
  \end{verbatim}
  The functions \texttt{modifyBoolValue}, \texttt{modifyDoubleValue}, \texttt{modifyIntegerValue}, and \texttt{modifyStringValue} all have the same form, with the two arguments indicating the name of the option and the value to which you would like to set it, respectively.
  \item In an options file. After a \texttt{NonOptSolver} object has been declared, one can modify the value of \emph{multiple} options via a statement such as:
  \begin{verbatim}
  nonopt.options()->modifyOptionsFromFile("nonopt.opt");
  \end{verbatim}
  Here, \texttt{nonopt.opt} represents the name of a file containing a list of options and the values to which you would like to set them.  For example, the contents of the file might be:
  \begin{verbatim}
  cpu_time_limit 600.0
  iteration_limit 1e+4
  \end{verbatim}
  Each line should contain only the name of an option followed by the desired value.
\end{itemize}

The same methods are available from Python on the object returned by \texttt{solver.options()}, with identical names and arguments, e.g.:
\begin{verbatim}
solver.options().modifyDoubleValue("cpu_time_limit", 600.0)
solver.options().modifyOptionsFromFile("nonoptpy.opt")
\end{verbatim}

As previously mentioned, a useful option is to turn on the derivative checker, which is off by default. The default derivative checker option is \texttt{FiniteDifference}. Assuming this is the derivative checker that has been chosen, the derivative checker can be turned on by the statement:
\begin{verbatim}
nonopt.options()->modifyBoolValue("DEFD_check_derivatives", true);
\end{verbatim}
or within an options file by including the line:
\begin{verbatim}
DEFD_check_derivatives true
\end{verbatim}
The derivative checker can be computationally expensive, so it is not recommended to run the derivative checker when performing timed experiments. But it is the best first step for debugging!

\section{NonOpt Reporter Output}\label{sec.output}

The option \texttt{print\_level} determines the level of output to be printed to standard output.  Setting this level to \texttt{0} means that no information will be printed.  Setting this level to \texttt{1} means that a basic amount of information will be printed, such as in the example below.  The information at this level is self-explanatory, perhaps except for the EXIT messages, which are summarized after the example.

\begin{verbatim}
  +--------------------------------------------------------------+
  |       NonOpt = Nonlinear/Nonconvex/Nonsmooth Optimizer       |
  | NonOpt is released as open source code under the MIT License |
  |     Please visit: https://github.com/frankecurtis/NonOpt     |
  +--------------------------------------------------------------+

  This is NonOpt version 2.2

  Number of variables.................. : 1000
  Initial objective.................... : 6.908755e+00
  Initial objective (unscaled)......... : 6.908755e+00

  Approximate Hessian update strategy.. : BFGS
  Derivative checker strategy.......... : FiniteDifference
  Direction computation strategy....... : CuttingPlane
  Line search strategy................. : WeakWolfe
  Point set update strategy............ : Proximity
  QP solver (small scale) strategy..... : DualActiveSet
  QP solver (large scale) strategy..... : InteriorPoint
  Symmetric matrix strategy............ : Dense
  Termination strategy................. : Basic

  EXIT: Stationary point found.

  Objective............................ : 3.008077e-09
  Objective (unscaled)................. : 3.008077e-09

  Number of inner iterations........... : 25
  Number of QP iterations.............. : 29

  CPU seconds in line searches......... : 0.008766
\end{verbatim}

There are various EXIT messages that may be printed, which indicate the reason that the \texttt{NonOptSolver} terminated.  Some messages end with the phrase ``\texttt{This wasn't supposed to happen!}''  If any of those are printed, then we ask the user to contact \href{mailto:frank.e.curtis@gmail.com}{Frank E. Curtis}, since that was not supposed to happen!  With respect to the EXIT messages that are intended to be printed, their meanings are the following.

\begin{itemize}
  \item \texttt{Stationary point found}: A point has been found satisfying the stationarity conditions; see, e.g., \cite{CurtRobiZhou20}.
  \item \texttt{Objective not improving sufficiently}: The objective has not improved sufficiently in recent iterations, indicating that the algorithm is not likely to make substantial further progress.
  \item \texttt{Objective tolerance reached}: A point has been found whose objective value is below a tolerance that has been provided by the user.
  \item \texttt{CPU time limit reached}: The CPU time limit has been reached.
  \item \texttt{Iterates seem to be diverging}: A point has been found whose norm is above a tolerance.
  \item \texttt{Iteration limit reached}: The iteration limit has been reached.
  \item \texttt{Function evaluation limit reached}: The function evaluation limit has been reached.
  \item \texttt{Gradient evaluation limit reached}:  The gradient evaluation limit has been reached.
  \item \texttt{Approximate Hessian update failure}: A failure occurred, due to a numerical tolerance being violated, in the update of the approximate Hessian matrix.  By default, the code would not terminate based on such a tolerance, so this would only occur if a user turns this feature on as a termination condition.
  \item \texttt{Derivative checker failure}: A failure occurred, due to a numerical tolerance being violated, in the derivative checker.  By default, the code would not terminate based on such a tolerance, so this would only occur if a user turns this feature on as a termination condition.
  \item \texttt{Direction computation failure}: A failure occurred, due to a numerical tolerance being violated, in the direction computation.  By default, the code would not terminate based on such a tolerance, so this would only occur if a user turns this feature on as a termination condition.
  \item \texttt{Function evaluation failure! Check definition of problem}: An error occurred in the function evaluation code provided by the user.
  \item \texttt{Gradient evaluation failure! Check definition of problem}: An error occurred in the gradient evaluation code provided by the user.
  \item \texttt{Line search failure}: A failure occurred, due to a numerical tolerance being violated, in the line search.  By default, the code would not terminate based on such a tolerance, so this would only occur if a user turns this feature on as a termination condition.
  \item \texttt{Point set update failure}: A failure occurred, due to a numerical tolerance being violated, in the point set update.  By default, the code would not terminate based on such a tolerance, so this would only occur if a user turns this feature on as a termination condition.
  \item \texttt{Problem data read failure!  Check definition of problem}: An error occurred in the code provided by the user.
  \item \texttt{Termination check failure}: A failure occurred, due to a numerical tolerance being violated, in the termination checker.  By default, the code would not terminate based on such a tolerance, so this would only occur if a user turns this feature on as a termination condition.
\end{itemize}

When NonOpt is used from Python, the same information is available programmatically through \texttt{solver.status()}, which returns a value of the \texttt{nonoptpy.NonOpt\_Status} enumeration corresponding to the EXIT message; see \S\ref{sec.python}.

Setting \texttt{print\_level} to \texttt{2} means that per-iteration output will be printed in addition to the basic output shown above.  A header line is printed periodically to indicate the meaning of the values in each column of the per-iteration output.  Further information about these quantities is provided in the list below.  The per-iteration output when the \texttt{direction\_computation} option is set to either \texttt{CuttingPlane} or \texttt{GradientCombination} is exactly the same, whereas when this option is set to \texttt{Gradient} the column \texttt{L?} is omitted since the small-scale QP subproblem solver is always employed for this strategy.

\begin{itemize}
  \item \texttt{Iter.}: iteration index
  \item \texttt{Objective}: objective function value
  \item \texttt{St. Rad.}: stationarity radius
  \item \texttt{Tr. Rad.}: trust region radius
  \item \texttt{|Pts|}: cardinality of point set
  \item \texttt{In Its}: inner iteration index in direction computation method
  \item \texttt{QP Pts}: cardinality of points used to build QP subproblem
  \item \texttt{L?}: indicator that QP is large scale (\texttt{1}) or not (\texttt{0})
  \item \texttt{QP Its}: iterations required to solve QP subproblem
  \item \texttt{S?}: termination status of QP subproblem solver (\texttt{0} indicates success)
  \item \texttt{QP KKT}: QP subproblem solution KKT error
  \item \texttt{|Step|}: norm of search direction
  \item \texttt{|Step|\_H}: norm of search direction, with norm defined by approximate Hessian
  \item \texttt{|Grad.|}: norm of objective gradient
  \item \texttt{|G. Cmb.|}: norm of combination of gradients corresponding to QP subproblem solution
  \item \texttt{Stepsize}: step size from line search
  \item \texttt{Up. Fact.}: approximate Hessian update factor
  \item \texttt{U?}: indicator that approximate Hessian update is being updated (\texttt{1}) or not (\texttt{0})
\end{itemize}
